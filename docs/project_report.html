Why this exists

CloudFlow needed one number everyone could trust

CloudFlow sells three product lines — Core Platform, Analytics Add-on, and Automation Suite — across four pricing tiers to customers ranging from self-serve startups to negotiated enterprise contracts, in five regions. Revenue comes from new sales, renewals, expansion, and is offset by churn — and before this system existed, answering "what will next quarter look like" meant someone manually reconciling exports from billing, usage, and CRM systems.

The brief was simple to state and hard to do honestly: build a single pipeline from source data to forecast, pick a model on evidence rather than intuition, and put it in front of the team as a dashboard they'd actually use — not a one-off spreadsheet that goes stale the day someone closes it.

How it's built

Six phases, one MySQL database, no shortcuts

Every stage reads from and writes to the database — the source CSVs are touched exactly once, at ingestion. Nothing downstream ever reads a spreadsheet again.

1
Ingest src/ingest_csv.py
Create the database, stage each of the 9 source CSVs into its own raw table, and validate row counts, referential integrity, and date ranges before anything downstream runs.
2
Process src/process_data.py
Clean and type the raw tables into proper dimension/fact tables and a monthly revenue summary, reconciling every dollar back to the source transactions.
3
Engineer features src/feature_engineering.py
Build the ML feature table — every single predictor is lagged one month behind the target, so the model can never accidentally see the future during training.
4
Evaluate src/evaluate_model.py
Backtest all seven candidate models with an expanding walk-forward window and score them on the same 12 held-out months.
5
Forecast src/forecast.py
Refit the winning model on the full history and roll it forward six months with an 80% confidence interval.
6
Serve app.py
A Streamlit dashboard reads only the finished output tables — never the raw data — through a single query layer.

Choosing a model honestly

The simplest model won — and that's the honest result

Rather than reaching for gradient boosting by default, seven models were backtested against the same 12 months, one month at a time, each one trained only on data that would have actually been available at that point in history.

ModelTypeMAPE
driftBaseline — last value + average trend2.18%Selected
holt_linearClassical exponential smoothing2.19%
naiveBaseline — last observed value2.70%
moving_avg_3Baseline — trailing 3-month mean3.65%
xgboostGradient-boosted trees4.16%
lightgbmGradient-boosted trees7.84%
seasonal_naiveBaseline — value 12 months prior20.50%

Why a simple baseline beat two gradient-boosted models: CloudFlow's 59 months of revenue are smooth and trend-dominated, without the sharp seasonality or nonlinear interactions that give tree models something to exploit — drift and holt_linear finish within a hundredth of a point of each other, while XGBoost and LightGBM trail by roughly 2x and 3.5x respectively. Reporting the honest winner — instead of quietly defaulting to whichever model sounds most sophisticated — is the difference between a forecast you can trust and one that just looks impressive.

What the team sees

One dashboard, actuals and predictions kept strictly apart

The Dashboard page shows only what happened — filterable by date, segment, region, and product, with every KPI backed by a source-and-formula panel on request. The Revenue Forecast page shows only predictions, so no one can mistake a forward-looking number for a historical one.

Ask it a question

A chatbot that isn't allowed to make numbers up

A floating assistant sits on every page. It doesn't generate answers from memory — every response is grounded in a live query against the actual database, and every query is checked before it runs.

Question
→
Groq drafts SQL
→
sql_guard.py checks it
→
Read-only query runs
→
Answer, grounded in the result

sql_guard.py rejects anything that isn't a single, read-only SELECT, blocks a keyword blacklist, forces the session read-only, and caps results at 200 rows — before the query ever reaches MySQL. If a question falls outside what the data can answer, the assistant says so, rather than guessing.
